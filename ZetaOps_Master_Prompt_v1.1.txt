-- CRITICAL HEADER RULES -------------------------------------------------------
NEVER use these characters in any comment or header - they break parsers:
- Em dash: -- (U+2014) -> use hyphen - instead
- En dash: - (U+2013) -> use hyphen - instead
- Box drawing: --- === | (U+2500-U+257F) -> use plain - or = instead
- Left arrow: <- (U+2190) -> use <- instead
- Backtick fence: ``` -> never use inside source files
- Curly quotes: " " ' ' -> use straight quotes " ' instead

Python files: headers are # comments only. Never use """ docstrings as file
headers - they cause SyntaxError in some Python versions when placed at module
level with special characters.

SECTION 2 -- BACKEND DESIGN PRINCIPLES
================================================================================
1.  BACKEND COMPUTES, FRONTEND DISPLAYS
    The backend engine computes all scheduling logic, cost calculations,
    conflict detection, and availability. Frontend only renders what the backend
    returns. Never recompute backend logic in frontend components.

2.  TENANT ISOLATION IS MANDATORY
    Every DB query must filter by tenant_id. No exceptions.
    Pattern: db.query(Model).filter(Model.tenant_id == current_user.tenant_id)
    If you forget tenant_id, one tenant sees another's data. This is a critical bug.

3.  SECRETS NEVER IN CODE
    SECRET_KEY, GROQ_API_KEY, DATABASE_URL, ANTHROPIC_API_KEY all come from
    .env via Settings (pydantic-settings). Never hardcode.
    Settings uses extra="ignore" so unknown .env keys don't cause ValidationError.

4.  ALL API ROUTES HAVE /api/ PREFIX
    Exception: /auth/* and /dashboard/plan-limits (registered without prefix).
    Every new router must be registered in main.py with prefix="/api/routername".

5.  RESOURCE AVAILABILITY != SCHEDULING CONFLICTS
    Availability (amber/red %) = how much of a resource is free on given dates.
    Scheduling conflict = the engine cannot fit a step due to overlap or deadline.
    These are different systems. availability_engine.py != scheduler/engine.py.

6.  MIGRATIONS ARE APPEND-ONLY
    Never edit an existing migration file. Always create a new one.
    Migration chain must always have exactly ONE head.
    After adding a migration: alembic heads -> must show exactly one revision.
    Naming: NNN_description.py where NNN is next sequential number.

7.  PYDANTIC V2 STYLE EVERYWHERE
    Use model_config = {...} not class Config.
    Use datetime.now(UTC) not datetime.utcnow().
    Use Optional[str] = None not str = None for optional fields.

8.  FEATURE FLAGS GATE EVERYTHING
    New features start with flag=False in features_config.py.
    Backend: use @require_feature("flag_name") decorator.
    Frontend: check useFeatureFlags() before rendering.
    Never ship a feature without a flag.

9.  PLAN LIMITS ARE ENFORCED DUAL-LAYER
    Backend: returns HTTP 402 when limit reached.
    Frontend: LimitedButton + PlanLimitBanner disable UI before the API call.
    Both layers must be kept in sync.

10. SCAN PAGE IS ALWAYS PUBLIC
    /scan route has no auth. Never add authentication to ScanPage.tsx or the
    /api/scan/* endpoints. Printed QR codes must always be scannable.

SECTION 4 -- TYPESCRIPT ERROR HANDLING RULES (added v1.1)
================================================================================
These rules come from real bugs found and fixed in the codebase. Violating
them causes TypeScript errors in strict mode or silent runtime failures.

16. ALWAYS USE axios.isAxiosError() IN CATCH BLOCKS
    TypeScript strict mode types catch block errors as unknown.
    Never access .response on an unknown error directly.

    WRONG - causes TS error and may crash at runtime:
      } catch (err) {
        const msg = err?.response?.data?.detail  // TS error: err is unknown
      }

    WRONG - unsafe cast, TypeScript won't catch mismatches:
      } catch (err) {
        const msg = (err as { response?: { data?: { detail?: string } } })
          ?.response?.data?.detail
      }

    CORRECT - type-safe, runtime-safe:
      import axios from 'axios'
      } catch (err: unknown) {
        const msg = axios.isAxiosError(err)
          ? err.response?.data?.detail
          : undefined
        setError(msg ?? 'Something went wrong')
      }

    CORRECT - for non-Axios errors (e.g. localStorage, JSON.parse):
      } catch (err: unknown) {
        const msg = err instanceof Error ? err.message : 'Unknown error'
      }

    RULE: Every catch block that accesses err must use one of:
      - axios.isAxiosError(err) for Axios/API errors
      - err instanceof Error for generic JS errors
      Never use "as" casts on caught errors.

17. ALWAYS IMPORT axios WHEN USING isAxiosError
    axios.isAxiosError() requires axios to be imported in the same file.
    If you add error handling to a file, add the import too.

    import axios from 'axios'  // required for isAxiosError

    Files that MUST have this import (all make API calls):
    - All pages/ files with try/catch around apiClient calls
    - All components/ files with try/catch around apiClient calls
    - Any file using useMutation with onError handler

18. CATCH BLOCK PATTERNS BY USE CASE

    API call - show error to user:
      } catch (err: unknown) {
        const msg = axios.isAxiosError(err)
          ? (err.response?.data?.detail ?? 'Request failed')
          : 'Something went wrong'
        setError(msg)
      }

    API call - show toast notification:
      } catch (err: unknown) {
        const msg = axios.isAxiosError(err)
          ? (err.response?.data?.detail ?? `Failed to ${action}`)
          : `Failed to ${action}`
        showToast(msg, 'error')
      }

    API call in onError (TanStack mutation):
      onError: (err: unknown) => {
        const msg = axios.isAxiosError(err)
          ? (err.response?.data?.detail ?? 'Operation failed')
          : 'Operation failed'
        setError(msg)
      }

    Non-fatal / silent catch (localStorage, optional fetch):
      } catch { }           // empty catch - no variable needed, no TS error
      } catch (_) { }       // underscore prefix - explicitly ignored

    DOM / browser API errors:
      .catch(e => setError(e instanceof Error ? e.message : 'Failed to load'))

    Token refresh in axios interceptor (client.ts):
      } catch (refreshError: unknown) {   // must type as unknown
        processQueue(refreshError, null)
        tokenStore.set(null)
        window.location.href = '/login'
      }

19. COMPONENT PROPS MUST BE TYPED BEFORE USE
    Every React component must have an explicit props interface defined
    BEFORE the component function. Never write props inline or omit them.

    WRONG:
      export default function MyComponent() {  // no props = TS error when
      }                                        // caller passes props

    CORRECT:
      interface MyComponentProps {
        count:        number
        label?:       string   // optional with default
        onAction?:    () => void
      }
      export default function MyComponent({
        count,
        label   = 'default',
        onAction,
      }: MyComponentProps) {
      }

    RULE: Define the interface first, then the component. The interface is
    the contract. Optional props use ? and must have default values in
    destructuring.

20. NEVER USE "as const" ON UNION TYPE FIELDS IN OBJECT LITERALS
    "as const" narrows a value to its exact literal type, making it
    incompatible with the wider union type the field expects.

    WRONG - over-narrows to literal 'pick_a_date', breaks assignment:
      const emptyForm = {
        start_mode: 'pick_a_date' as const,  // type: 'pick_a_date'
      }

    CORRECT - cast to the full union type:
      const emptyForm = {
        start_mode: 'pick_a_date' as 'right_away' | 'pick_a_date' | 'flexible',
      }

    OR import and use the named type:
      import type { StartMode } from '../types/types_index'
      const emptyForm = {
        start_mode: 'pick_a_date' as StartMode,
      }

    RULE: Use "as const" only for truly readonly config objects where you
    WANT the narrowest type. For form state or mutable fields, cast to the
    full union type.

21. REACT EVENTS VS NATIVE DOM EVENTS - NEVER MIX
    React synthetic events (JSX handlers) and native DOM events
    (window/document listeners) are different TypeScript types.

    JSX handler -> React synthetic event:
      function handleClick(e: React.MouseEvent<HTMLButtonElement>) { }
      <button onMouseDown={handleClick} />   // correct

    window.addEventListener -> native DOM event:
      function onMouseMove(e: globalThis.MouseEvent) { }  // NOT React.MouseEvent
      window.addEventListener('mousemove', onMouseMove)   // correct

    WRONG - mixing types causes TS error:
      import { type MouseEvent } from 'react'
      function onMouseMove(e: MouseEvent) { }         // React type
      window.addEventListener('mousemove', onMouseMove) // TS error

    RULE:
    - JSX props (onClick, onMouseDown etc) -> React.MouseEvent<Element, ...>
    - window/document.addEventListener   -> globalThis.MouseEvent
    - Never import React's MouseEvent and use it for window listeners.
    - Remove React MouseEvent from imports if only used for window listeners.

22. showToast SIGNATURE - ALWAYS MATCH DEFINITION
    showToast is defined locally in each page with this signature:
      const showToast = (msg: string, _type: 'success' | 'error' = 'success') => {
        setToast(msg)
        setTimeout(() => setToast(''), 3500)
      }

    The second argument _type is prefixed with _ because it is not yet wired
    to styling. This silences the noUnusedParameters TypeScript error.
    Call it as: showToast('message') or showToast('message', 'error')
    Never call it with a third argument.
    Never remove the _type parameter - callers pass it for future use.

23. ALL SHARED TYPES GO IN types_index.ts - NEVER INLINE
    If the same interface is defined in more than one file, it belongs in
    frontend/src/types/types_index.ts.

    Common types that MUST be in types_index.ts (not inline):
    - SkillReq, RawMaterial, AssignedEmployee, AssignedMachine
    - Job, DashboardJob, DashboardData
    - FeasibilityResult, FeasibilityConflict
    - StartMode, TimerStatus, JobStatus
    - Employee, Machine, Skill, EmployeeSkill
    - PlanLimits, JobStep, AvailabilityOverride

    When adding a new shared type:
    1. Add it to types_index.ts with export
    2. Import it in all files that need it
    3. Delete any duplicate inline definitions

    When fixing "Property X does not exist on type Y":
    - First check if X is missing from types_index.ts
    - Add the missing field (nullable if API may not return it: string | null)
    - Never add the field only to the local inline interface

24. API FILES MUST LIVE IN frontend/src/api/ ONLY
    All API module files belong in frontend/src/api/.
    File naming convention: api_<resource>.ts
      api_employees.ts, api_machines.ts, api_jobs.ts,
      api_skills.ts, api_dashboard.ts, api_timer.ts,
      api_resource_availability.ts, api_gantt.ts

    WRONG - file at project root or wrong folder:
      msme-resource-scheduler/api_employees.ts  // root - wrong
      frontend/api_employees.ts                  // wrong folder

    CORRECT:
      frontend/src/api/api_employees.ts          // correct

    If a file exists at the project root AND in frontend/src/api/:
    - Compare file sizes and dates
    - Keep the newer/larger version in frontend/src/api/
    - Delete the root copy

25. LUCIDE ICONS MUST BE IMPORTED BEFORE USE
    Every icon used in JSX must be in the import statement for that file.
    TypeScript will error with "Cannot find name 'X'" if missing.

    Common icons used across this codebase - add any you use:
      import {
        Pause, Play, Square, RotateCcw, CheckCircle2,
        AlertCircle, Loader2, Clock, CalendarDays,
        Zap, BriefcaseBusiness, TrendingUp, TrendingDown,
        ChevronUp, ChevronDown, Factory, Users,
        Plus, Pencil, Trash2, X, Check, Search,
      } from 'lucide-react'

    RULE: When adding a new icon to a component, add the import immediately
    before writing any JSX. Do not leave imports for later.
    Current lucide-react version: ^0.577.0 - all common icons available.

SECTION 7 -- ALEMBIC MIGRATION RULES
================================================================================
BEFORE WRITING A MIGRATION
  alembic heads    # must show single head
  alembic current  # shows current DB revision
  alembic history  # shows full chain

CREATING A NEW MIGRATION
  Always create manually - never use autogenerate in production
  Copy the last migration file, increment the number
  File naming: NNN_describe_what_changes.py
  Set revision and down_revision correctly
  Write both upgrade() and downgrade()

AFTER WRITING A MIGRATION
  alembic upgrade head                                         # apply to dev DB
  alembic heads                                                # must still show single head
  python -m py_compile alembic/versions/NNN_new_migration.py  # no syntax errors

MIGRATION FILE HEADER (clean, no special chars)
  # alembic/versions/NNN_description.py
  # Migration: short description
  # Introduced in: v4.0.X
  # What it does: adds X column to Y table

NEVER
  Edit an existing migration that has been run in any environment.
  Delete a migration file.
  Use non-ASCII characters in migration files.
  Merge two migration files into one.
