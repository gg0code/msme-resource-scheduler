## Migration applied

- **028 — events table.** Schema:
  - `id`            INT PK
  - `tenant_id`     INT FK tenants.id ON DELETE CASCADE
  - `event_type`    VARCHAR(50) — dotted ('user.invited', 'user.role_changed', 'user.deactivated', future 'briefing.sent')
  - `entity_type`   VARCHAR(50) — 'user' for v6.3.3
  - `entity_id`     INT NULL — pointer to the affected row (no FK; entity_type is the discriminator)
  - `actor_user_id` INT FK users.id ON DELETE SET NULL — preserves audit history when a user is purged
  - `source`        VARCHAR(20) — 'web' for v6.3.3; 'whatsapp' / 'system' reserved for later
  - `payload`       JSONB NULL — free-form event-specific dict (patched to JSON for SQLite tests)
  - `created_at`    TIMESTAMPTZ NOT NULL DEFAULT now() — patched to CURRENT_TIMESTAMP for SQLite tests
- Indexes: `idx_events_tenant_id`, `idx_events_tenant_event_type`, `idx_events_entity` (entity_type+entity_id).
- v6.3.4+ briefing dispatch and other event sources reuse this table — no further migration needed.

## Three new endpoints — request/response shapes

### `GET /api/team`
Permission: `require_top_tier()`
Returns: `TeamMemberOut[]` ordered by id.

### `POST /api/team/invite`
Permission: `require_top_tier()` + handler check that only owner/proprietor may grant TOP_TIER_ROLES.
Request:
```json
{ "email_or_phone": "user@example.com" | "+919876543210", "role": "manager" }
```
Response (201):
```json
{
  "member": { "id": 42, "email": "...", "phone_e164": null, "role": "manager", "is_active": true, "is_top_tier": false, "created_via": "web_invite" },
  "temp_password": "<one-time-only-shown>" | null
}
```
`temp_password` is `null` for phone-only invites (whatsapp-first user pattern - no password, authenticates via WhatsApp identity later).

### `PATCH /api/team/{user_id}/role`
Permission: same as invite. Last-owner protection: refuses (400) when demoting the sole active top-tier user out of top-tier.
Request: `{ "role": "factory_manager" }`
Response: `TeamMemberOut`.

### `DELETE /api/team/{user_id}`
Permission: `require_role('proprietor', 'owner')` (tighter than the others - even factory_manager and co_owner cannot remove members per SRS Section 6.28.6).
Soft-delete: sets `is_active=False`. Last-owner protection: refuses (400) for the sole active top-tier user.
Response: 204 No Content.

## Decisions made

### 1. Added a fourth helper `require_operational()` — not in the original prompt

**Why:** The prompt's binary "Operational → require_top_tier()" rule conflated two
existing gates that meant different things:
- `require_role('proprietor', 'scheduler')` (26 sites) - allowed proprietor + scheduler
- `require_role('proprietor')` (6 sites) - proprietor only

Switching all 32 sites to `require_top_tier()` would have removed
scheduler/manager access from 26 endpoints, breaking the existing
1 dev-DB scheduler user (and likely more in production). The user
explicitly chose Path B at the planning stage: keep both spellings as
synonyms for v6.3.3 and consolidate names later. `require_operational()`
preserves scheduler access AND extends to the v6.4 top-tier roles plus
the v6.4 'manager' spelling.

`OPERATIONAL_ROLES = (*TOP_TIER_ROLES, 'scheduler', 'manager')` lives in
`dependencies.py` so future iterations can adjust without touching every
gate site.

### 2. Soft-delete via `is_active=False` for `DELETE /api/team/{id}`

The prompt said "DELETE" but did not specify hard vs soft. Soft-delete
chosen because:
- Hard delete would NULL `actor_user_id` on every event the user produced
  (per the FK SET NULL on `events.actor_user_id`) - audit history loses
  one of its two key anchors.
- Login already gates on `is_active`, so soft-delete is sufficient to
  block access.
- Reversal path: a future "restore member" endpoint can flip the bit back.

### 3. Phone-only invites synthesise placeholder email

`User.email` is NOT NULL UNIQUE. Phone-path invites don't have an email
yet, so the service writes `+invite-<8hex>@whatsapp.local` (same idiom
as `auth_service.register_tenant_and_user` for whatsapp_first signups).
The placeholder is recognisable in the DB and gets overwritten when the
user adds a real email later.

### 4. CHECK 4 returns 0 (informational), not 1 (hard fail)

CHECK 4 finds 2 dev-DB tenants with zero active top-tier users. These
tenants were already locked out of `require_role('proprietor')` endpoints
pre-v6.3.3 - the diagnostic surfaces a real pre-existing data state, not
a v6.3.3 regression. Making CHECK 4 fail the script would block the
pre-tag gate on a data-state issue unrelated to this iteration. WARNING
output is loud enough that operators will notice and act.

### 5. `require_billing_view()` defined now, used later

No current endpoint exposes commercial data, so this helper has zero
callers in v6.3.3. Defined now so v6.3.4 (briefing config) and v6.3.5+
(plan management) can `Depends(require_billing_view())` without needing
to re-derive the (owner, proprietor, co_owner) tuple. Pure addition;
no risk.

### 6a. Synthesised invite email format had to pass Pydantic EmailStr (mid-iteration fix)

After Decision 6 made phone-only invitees log in via password, manual
testing surfaced two `email-validator` rejections in sequence:

1. **Leading `+`** in `+invite-XXX@whatsapp.local` - `email-validator`
   rejects local parts starting with `+`. The auth_service synthesis
   pattern `{slug}+nomail@whatsapp.local` works because the `+` is in
   the *middle* (standard email-alias form). Fixed by dropping the
   leading `+`.
2. **`.local` TLD** - rejected as a "special-use or reserved name"
   per RFC 6761. Same applies to `.test`, `.invalid`, `.example`,
   `.localhost`. The auth_service uses `.local` because those users
   never log in by password (empty hash); for invitees who DO log in,
   the synthesised string must pass EmailStr.

Final format: `invite-<8hex>@invite.zetaops.com`. Real TLD,
recognisable subdomain prefix, no real mailbox needed (no email is
ever sent to this address - it is purely a unique key in the users
table). New regression test
`test_synthesized_invite_email_passes_pydantic_emailstr` pipes the
synthesised string through the same `EmailStr` validator
`/auth/login` uses, so any future format change that breaks login
fails at test time, not in manual testing.

### 6. Phone-only invites also get a temp password (mid-iteration fix)

Initial implementation matched `auth_service.register_tenant_and_user`'s
whatsapp_first pattern: phone-only invites stored an empty hash and
returned `temp_password=null`, on the assumption the invitee would
authenticate via the WhatsApp HAAN flow. Manual testing surfaced that
HAAN does not ship until v6.3.5 - which made phone-only invitees
**unreachable** (no password, no working WhatsApp auth). Service now
always issues a temp password regardless of email-or-phone path. The
WhatsApp HAAN flow, when it lands, will be a *second* auth channel
rather than the only one. UI also updated to show both the synthesized
email and the password in the one-time credentials panel so the
inviter can paste both into a message.

Test `test_invite_phone_only_creates_no_temp_password` was renamed and
its assertion flipped to lock the new behaviour.

### 7. Removed dead `TOP_TIER_ROLES` import from `role_helpers.py`

After removing the duplicate definition (Lesson 22), the import was
unused. Lesson 1 / "no dead code" - removed cleanly. The module's
docstring still references TOP_TIER_ROLES as the canonical set in
`app.models.auth`.

## Lessons learned in v6.3.3 (carry forward to v6.3.4+)

### Lesson 27 — Audit prompts that prescribe a binary mapping over an N-ary reality

The v6.3.3 prompt said "Operational → require_top_tier()". The
codebase had TWO existing gates that both meant "operational" but
admitted different role sets. Blindly applying the prompt's binary
would have regressed scheduler access on 26 endpoints. **Always grep
first, count site by site, and surface mismatches before sweeping.**
Generalises Lesson 11: prompts assert codebase shape that is sometimes
wrong; verify before designing around the assertion.

**Apply for v6.3.4+:** When a prompt says "every X becomes Y", run the
distinct-values grep first. If X has ≥2 distinct shapes, the
substitution probably needs ≥2 outcomes. Surface that to the user
before doing the swap.

### Lesson 28 — Test counts in handoffs decay; measure fresh, every time

v6.3.3 prompt carried "25 role-limiting tests must still pass" from
v5.12 documentation. Actual count was 23. Same kind of stale carry as
v6.3.1 handoff's claimed 382 vs measured 386. **Pre-flight measurement
is the source of truth; the previous handoff is a hint.**

**Apply for v6.3.4+:** Pre-flight check 4 (pytest count) is the
authoritative baseline. Reconcile the predecessor handoff's number on
the spot, not later. Add note to handoff if discrepancy > 0.

### Lesson 29 — Diagnostic scripts surface real data findings; don't promote them to gate failures

CHECK 4 found 2 tenants with zero top-tier users. That is a real,
actionable finding — but it pre-dates v6.3.3 and would not be solved by
blocking the v6.3.3 tag. WARNING + return 0 is the right balance:
operator sees it, gate stays clean, nobody scrambles to fix
unrelated data right before a release.

**Apply for v6.3.4+:** Diagnostics that report on long-lived data
state (orphans, drift, lockout) should default to informational. Only
diagnostics that report iteration-specific schema mismatches (CHECK 2)
should hard-fail.

### Lesson 30 — Audit the helper-vs-data redundancy on every iteration touching role logic

`role_helpers.py` had a stale `TOP_TIER_ROLES` redefinition shadowing
the canonical import. Lesson 22 generalised to "no duplicate sources of
truth" - this iteration found and fixed one instance. Future iterations
touching role / permission code should grep for the same pattern
(`grep "= [\\(]" backend/app/services/role_helpers.py` and similar).

**Apply for v6.3.4+:** Before adding to any role/permission/limit
constant set, grep for ALL existing definitions of the same name.

### Lesson 31 — User-driven scope decisions go in the handoff verbatim

The user explicitly chose Path B (synonyms preserved, new helper added)
over Path A (consolidate names now). Recording that in Decision 1 above
keeps future iterations from re-litigating the same trade-off when
they hit `require_operational()` and wonder why the helper exists.

**Apply for v6.3.4+:** When the user chooses between options the prompt
did not specify, treat the choice as a "Decisions made" entry in the
handoff. The reasoning matters as much as the choice.
