# v6.3.4 - Daily Push Briefings - Handoff

**Date:** 2026-04-29
**Branch:** v5-whatsapp
**Predecessor tag:** v6.3.3
**Iteration:** 4 of 5 leading to v6.4
**Scope:** Wire the daily push briefings dispatcher. APScheduler runs
every 5 minutes, identifies tenants whose configured morning_time /
evening_time falls in the current window in the tenant's timezone,
generates industry-aware content (forward-looking morning,
backward-looking evening), resolves top-tier subscribed recipients,
sends via the existing WhatsApp wiring (mock-mode in dev), and writes
briefing.* events. Manual trigger via WhatsApp commands ("morning
briefing", "evening briefing", "aaj ka plan", etc.).

## Dispatcher API

```python
# Top-level cron entry (registered every 5 min in whatsapp_alerts.py)
async def dispatch_due_briefings(
    now_utc: datetime | None = None,
    *,
    sleep_fn: Callable[[float], Awaitable[None]] = asyncio.sleep,
    send_fn: Callable[[str, str, str], Awaitable[None]] | None = None,
    session_factory: Callable[[], Session] | None = None,
) -> DispatchSummary
```

```python
# Per-(tenant, kind) batch
async def dispatch_briefing(
    tenant: Tenant,
    kind: str,                     # 'morning' | 'evening'
    db: Session,
    *,
    today_in_tz: date | None = None,
    window_start_local: datetime | None = None,
    send_fn: ... | None = None,
    sleep_fn: ... = asyncio.sleep,
    enforce_window: bool = True,   # False on manual-trigger path
) -> BriefingDispatchResult
```

```python
# WhatsApp on-demand
async def manual_trigger_briefing(
    user: User,
    kind: str,
    db: Session,
    *,
    send_fn: ... | None = None,
    sleep_fn: ... = asyncio.sleep,
) -> str   # the briefing text - used as the WhatsApp reply
```

```python
@dataclass
class BriefingDispatchResult:
    kind: str
    sent_count: int = 0
    skipped_reasons: list[tuple[int | None, str]] = ...
    errors: list[tuple[int | None, str]] = ...

@dataclass
class DispatchSummary:
    tenants_processed: int = 0
    briefings_sent: int = 0
    briefings_skipped: int = 0
    skip_reasons: dict[str, int] = ...
```

## Event types added (4)

All entity_type='briefing', entity_id=NULL, polymorphic via payload.

| event_type | source | actor_user_id | payload |
|---|---|---|---|
| `briefing.sent` | `system` (cron) or `whatsapp` (manual) | NULL on cron, user.id on manual | `{kind, recipient_user_id, content_chars, [trigger='manual' on manual path]}` |
| `briefing.skipped` | `system` | NULL | `{kind, reason}`. v6.3.4 reasons: `'non_working_day'` only. (Disabled tenants skip silently - see Decision 1.) |
| `briefing.send_failed` | `system` | NULL | `{kind, recipient_user_id, attempts, error}` (error truncated to 500 chars) |
| `briefing.manual_trigger` | `whatsapp` | user.id | `{kind, requesting_user, content_chars}` |

The events for one manual trigger come in a pair: `briefing.manual_trigger`
(always fires - audit of the request) followed by `briefing.sent`
(only fires when the WhatsApp send succeeded; the `trigger='manual'` field
distinguishes from cron-fired sent rows).

## Decisions made

### 1. Disabled tenants skip silently - no `briefing.skipped` event

The prompt left this open ("no event written for skipped-disabled, OR
a `briefing.skipped` event with reason='disabled' - pick one and
document"). Chose silence. Reasoning:

- The dispatcher fires every 5 minutes. With 24 dev DB tenants at
  v6.3.4 launch, `briefing_morning_enabled=False` for nearly all of
  them, so each tick would write 24 `briefing.skipped` rows. Over 24
  hours that is 6912 rows of pure noise. The events table is the audit
  surface; flooding it makes legitimate audit work harder, not easier.
- The dispatcher still increments `summary.skip_reasons["disabled"]`
  in the in-memory summary returned to the caller (and logged at
  INFO), so ops can still see disabled-tenant counts on the cron tick.
- Working-day skip and no-recipients skip DO emit
  `briefing.skipped` events because those represent meaningful state
  for an operator: a working-day skip on a public holiday is exactly
  the kind of thing the operator wants to verify the briefing
  actually skipped; a no-recipients skip is the lockout-risk signal
  CHECK 4 already surfaces.

### 2. Stagger uses sorted-delta scheduling, not naive cumulative

Initial implementation slept the full per-tenant offset for every
tenant in the loop, so 22 tenants with average offset ~150s would
compound to ~55 minutes per tick. Fixed: sort tenants by offset, sleep
only the delta between consecutive tenants. Total wall-time per tick
is now bounded by `WINDOW_SECONDS=300` (5 minutes) regardless of
tenant count. Caught during the manual E2E run before tagging
(Lesson 39 - see below).

### 3. `hi` locale uses romanised Hindi, not Devanagari

CLAUDE.md "No Non-ASCII in Source Files" overrides any temptation to
write the templates in proper Devanagari. The `hi` locale strings are
romanised Hindi (e.g. "Suprabhat! Aaj ka plan -") - matching the
existing `whatsapp_alerts.py` and `whatsapp_checkin.py` convention
("abhi maintenance mode mein hai", "Subah ka briefing hua kya"). The
existing `whatsapp_responses.py` uses Devanagari via `\u` escapes; new
code I added there follows the same escape pattern.

### 4. Hours-logged in evening briefing not implemented

The prompt mentions "hours logged" as a desired evening-briefing line.
Skipped because `Job.timer_log` is a free-form JSON column with no
canonical schema across the v5.10 / v5.15 lineage; producing a number
here would be misleading. Documented in the file header
(`evening_content.py` "KEY DESIGN DECISIONS") so the next iteration
that codifies the timer-log schema can wire this in cleanly.

### 5. Industry vocabulary via labels dict, never via control flow

`INDUSTRY_LABELS` is a `dict[industry_type, dict[role, vocabulary]]`
that the morning + evening builders read once and pass through
templates. There is no `if industry_type == 'fabrication': ...`
anywhere in the briefings package. BUG-6 regression: industry comes
from `Tenant.industry_type`, never from any caller-supplied or
user-supplied value. Test `test_bug_6_industry_type_sourced_from_tenant_orm`
locks this contract.

### 6. `detect_briefing_request_intent` is a separate pure function

The prompt suggested "add intent `request_briefing` to detect_write_intent".
Made it a standalone function instead, kept in the same module. Reasons:

- `detect_write_intent` is sync; manual_trigger_briefing is async.
  Embedding the briefing call inside detect_write_intent would force
  the whole intent-detection layer async, which would touch every
  caller.
- The router already has a clear stage progression (consent ->
  language detection -> manager-checkin window -> write-intent ->
  AI). A briefing request belongs at its own stage (5c) before
  write-intent because the keyword overlap with role-gated keywords
  is real ("morning briefing" contains the word "morning" which is
  innocuous, but "today's plan" overlaps with planning-related
  keywords manager-tier might be blocked from). Detecting briefings
  first ensures top-tier users always get their briefing even if
  some other keyword would have led to a refusal.

### 7. Recipient resolution joins via PhoneTenantMap, not User.phone_e164

A user can have `User.phone_e164` set without ever having linked
through the WhatsApp HAAN flow - in that case `PhoneTenantMap` has no
matching row and the dispatcher would silently fail at send time. The
`resolve_recipients` join enforces "linked AND active phone" at
recipient-resolution time, so failures show up as
`briefing.skipped (no_recipients)` rather than send-time errors.

### 8. `freezegun` pinned in `requirements.txt` (single requirements file)

The repo has only `requirements.txt` (no `requirements-dev.txt`).
Added `freezegun==1.5.5` there. The file is UTF-16 LE encoded - new
line appended via PowerShell `Add-Content -Encoding Unicode` to
preserve encoding so pip continues to read it.

## Gotchas encountered

1. **The `INDUSTRY_LABELS` Devanagari-literal trap.** I initially wrote
   the `hi` locale strings with Devanagari characters and assumed the
   tooling would auto-escape on save. It did NOT - the file shipped
   with 300 non-ASCII bytes. Caught by `LANG=C tr -d '\000-\177' < f
   | wc -c`, fixed by rewriting `hi` locale strings as romanised Hindi
   (Decision 3). Lesson 36 below.

2. **The Read tool decodes `\u` escapes for display.** When verifying
   `whatsapp_responses.py`, the Read tool showed glyphs (e.g. devanagari-glyph...) for
   strings that were actually stored as Devanagari literals on disk.
   The byte-count check (300 non-ASCII bytes) caught the discrepancy.
   Lesson 37.

3. **Cumulative async-sleep silently breaks cron cadence.** First
   draft of `dispatch_due_briefings` slept the full per-tenant offset
   inside the loop. 22 tenants -> ~55 minutes per tick. Fixed during
   manual E2E (Decision 2). Lesson 39.

4. **`SessionLocal` in dispatcher prevents in-process testing.** The
   cron path opens its own sessions via `SessionLocal()` inside the
   function. Tests using the in-memory SQLite engine could not reach
   that orchestration. Solved by adding a `session_factory` keyword
   parameter (defaults to `SessionLocal`); tests pass a wrapper that
   yields the test session. Lesson 38.

5. **`patch_now_defaults_for_sqlite` autouse fixture must include
   every table the test touches.** Briefings query `Job` and
   `Employee`; the v6.3.3 fixture in `test_team_management.py` covered
   only `Tenant, User, RefreshToken, PhoneTenantMap, Event`. Adding
   `Job.__table__` and `Employee.__table__` to the sweep was required.

6. **`Tenant` ORM identity across sessions.** The cron path
   enumerates tenants on a list-session and dispatches per-tenant on a
   tenant-session. Tenants from the closed list-session are detached
   and SQLAlchemy refused queries on them. Fixed by re-fetching
   `tenant = tenant_db.get(Tenant, tenant.id)` at the top of each
   per-tenant block.

7. **`run_briefing_dispatch_tick()` exists ONLY to swallow exceptions.**
   APScheduler captures exceptions silently in some versions; centralising
   the try/except in this thin wrapper ensures any unexpected crash
   inside the dispatcher surfaces as a logged error rather than a
   silently swallowed schedule run.

## Lessons learned in v6.3.4 (carry forward to v6.3.5+)

### Lesson 35 - Stagger inside an async loop is a wall-time multiplier, not a parallel one

Initial dispatcher loop did `await sleep(offset)` per tenant. Total
wall-time per tick = sum of all offsets, not max. With 22 tenants and
average offset 150s, the tick would take ~55 minutes - silently
breaking the cron cadence. Fix: sort by offset, sleep only deltas, so
total tick wall-time is bounded by `WINDOW_SECONDS`.

**Apply for v6.3.5+:** Any time you put `await sleep(per_item_value)`
inside a loop, ask whether the total wall-time is what you want.
Either parallelise with `asyncio.gather` + per-item sleeps, or use
sorted-delta scheduling, or cap the cumulative budget.

### Lesson 36 - Verify ASCII compliance on bytes, not on Read-tool display

The Read tool decodes `\u` escapes back to glyphs for display. A file
that "looks ASCII" in Read may contain raw Devanagari/em-dash bytes on
disk. Use `LANG=C tr -d '\000-\177' < FILE | wc -c` (or equivalent
byte-level check) to verify, not visual inspection.

**Apply for v6.3.5+:** Before declaring "no non-ASCII in source
files," run the byte-level check on every changed file. The
verification step belongs in the per-fix protocol (Lesson 23).

### Lesson 37 - The auto-encoding behaviour of edit tools varies

When I wrote a Devanagari literal in an Edit `new_string`, one file's
content ended up as `\u` escapes on disk and another's stayed as raw
Devanagari. The behaviour appears to depend on whether the
surrounding context contained an existing escape pattern the tool
mirrored. Bottom line: do not rely on the tool's encoding choice;
write `\u` escapes explicitly when you want them.

**Apply for v6.3.5+:** Always write Hindi/Unicode strings as `\u`
escapes in source. Never trust the editor to "do the right thing."

### Lesson 38 - Dispatcher-orchestration code needs a session_factory injection point

Functions that open their own DB sessions (via `SessionLocal()`
imported inside the function body) cannot be tested against an
in-memory SQLite engine without monkey-patching. Add a
`session_factory: Callable[[], Session] | None = None` parameter to
every such function so tests can pass a wrapper that yields the test
session.

**Apply for v6.3.5+:** When a service-layer function needs to open
its own session (because the caller owns no session - cron, message
queue consumer, etc.), expose the session factory as an injectable
parameter. Default to `app.database.SessionLocal`; tests override.

### Lesson 39 - Manual E2E catches integration bugs unit tests cannot

The cumulative-stagger bug (Lesson 35) was missed by all 37 unit
tests - they all passed because they used a no-op `sleep_fn`. The bug
surfaced only when running `dispatch_due_briefings()` against the
real dev DB with the default (`asyncio.sleep`) sleep function.
Lesson 34 (manual E2E before tagging) paid for itself again: without
that step, the bug would have shipped and broken the production cron
cadence the moment v6.3.4 deployed.

**Apply for v6.3.5+:** Lesson 34 is non-negotiable. The unit tests
that injected stubs to make the test fast are exactly the tests that
miss timing-related bugs in the dispatch path. Manual E2E with
production defaults is the only way to catch them before the cron
fires for real.
