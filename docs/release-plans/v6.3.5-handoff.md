## Gotchas encountered

- **vi.mock + top-level fixtures**: vitest hoists vi.mock factories to
  the top of the file; any value referenced inside must come from
  `vi.hoisted()` (or be inlined in the factory). Fixed in
  `TeamAndRoles.test.tsx`.
- **react-hooks/set-state-in-effect**: My initial InviteMemberModal
  reset state via useEffect on `open` change. Lint blocked it. Fixed
  by resetting state at close-time via `resetAndClose()` instead - same
  outcome, no lint warning.
- **Em-dashes in code comments**: The Read tool decodes `\u` escapes
  for display, so I had three em-dashes in the modal header comments
  that looked fine on screen but failed the byte-level ASCII check
  (Lesson 36 / 37 again). Replaced with `-`.
- **Back-compat consent gate**: First pass made the consent check fire
  on inferred-channel WhatsApp invites, breaking the v6.3.3
  `test_invite_phone_only_returns_temp_password` test. Fixed by
  making `_resolve_channel` return `(channel, was_explicit)` and only
  enforcing consent + dispatching welcome when `was_explicit=True`.

## Bugs surfaced + fixed during manual E2E (Lesson 34 paid off)

The 12-step prompt called for a live browser walkthrough before tagging.
Running it surfaced three bugs that 537 unit tests + 4 router-E2E tests
never caught - exactly the scenario Lesson 39 warned about.

### Bug 1 (CRITICAL, pre-v6.3.5): WhatsApp consent handshake silently broken
**Files fixed:** `routers/whatsapp.py:723`, `services/whatsapp_identity.py:189-313`

**What was wrong:**
- `record_consent` was `async def` but used `await db.execute(...)` /
  `await db.commit()` against a **sync** `Session` (per CLAUDE.md
  whatsapp-services rule). That throws `TypeError` on the first await.
- The call site at `routers/whatsapp.py:723` ALSO forgot the `await`
  on the function call, so the orphan coroutine was garbage-collected
  with a `RuntimeWarning` that nobody saw.
- The handler returned the success message ("Shukriya! Aapki consent
  record ho gayi") regardless of whether the DB write actually
  happened - so logs looked clean and nobody noticed.

**Real-world impact (since v5.0):**
- Every WhatsApp user who replied HAAN had `consent_given` stay False.
- The `whatsapp_conversations` table was never written to (gated on
  the same flag via `check_consent`, which had the same bug).
- The Factory GPT training pipeline has been silently starved.
- `consent_at` audit timestamp has never been populated.

**Fix:** dropped the bogus `await`s on db calls inside both `check_consent`
and `record_consent`; added `await` at the call site. Verified by step 9
of `scripts/test_v6_3_5_onboarding.py` flipping status to `active`.

### Bug 2 (HIGH, pre-v6.3.5): 500 instead of 4xx on duplicate phone at signup
**File fixed:** `services/whatsapp_identity.link_phone_to_tenant`

**What was wrong:**
- `phone_tenant_map.phone_number` has a **column-level** `unique=True`
  constraint (global uniqueness), but the existence check filtered by
  `phone_number == X AND tenant_id == X`. Any cross-tenant collision
  slipped past the Python check, then PostgreSQL killed the INSERT
  with `IntegrityError`. FastAPI returned bare `500 Internal Server
  Error` (not even JSON).

**Real-world impact:**
- Genuine retry attempts (form double-submit, two tenants claiming
  the same number) get a 500 instead of "phone already in use".
- Frontend RegisterPage error handler can't surface a useful message.
- Information-leak smell on a public endpoint.

**Fix:** changed `link_phone_to_tenant` existence check to filter by
`phone_number` alone. Existing `except PhoneAlreadyLinkedError` handlers
in `auth_service.register_tenant_and_user` and v6.3.5 `team_service.invite_member`
now correctly surface 400 / 409 to the client. Manual probe with
`+919876543210` (the test tenant's phone) now returns 400 with
`"Phone +919876543210 is already linked to another tenant."`.

### Bug 3 (MEDIUM, v6.3.5 regression): deleted users stayed visible in Team & Roles
**File fixed:** `frontend/src/pages/settings/TeamAndRoles.tsx`

**What was wrong:**
- `team_service.delete_member` is a soft-delete (sets `is_active=False`)
  to preserve the events-table FK to `users.id`.
- The v6.3.3 Team & Roles page had a Status column that explicitly
  showed "Inactive" for soft-deleted rows.
- The v6.3.5 redesign dropped that column without replacing the
  indicator. Soft-deleted rows continued to appear in the table with
  no clear "Removed" cue - just a slightly faded role pill (because
  the `<select>` was disabled). Users reasonably interpreted the
  delete button as not working.

**Fix:** added `members.filter(m => m.is_active)` to the table render.
Backend still returns the full list for audit consumers; the table now
shows only active members. The soft-delete model is preserved for the
events-table FK invariant.

### Pattern across all three bugs
All three bugs were dormant because the verification surface didn't
exercise them:
- Bug 1: Pytest tests ran with mocked `_send_alert`; nobody ran a real
  HAAN handshake against a real DB and re-queried `consent_given`.
- Bug 2: Pytest tests used unique phones per test; nobody tried to
  register a phone that another tenant already owned.
- Bug 3: Vitest component tests used fixtures with `is_active: true`;
  nobody clicked the delete button in a live browser and watched the
  table.

**Lesson 39 (live E2E catches what unit tests cannot) earned its keep
in this iteration.** Lesson 45 below codifies the takeaway.

## Lessons learned in v6.3.5 (continuing from Lesson 39)

- **Lesson 40** - When changing a service-layer return shape, grep ALL
  callers FIRST. The 3-tuple change in `invite_member` looked clean in
  isolation; only running test_team_management.py revealed it broke
  every existing call site that unpacked as a 2-tuple. Default to
  zero-blast-radius signature changes: extend with helper functions,
  do not rewrite the existing one.

- **Lesson 41** - Back-compat needs an "explicit vs inferred" axis.
  When adding new optional fields whose presence changes behaviour
  (`channel`, `consent_given`), distinguishing "caller did not set
  this" from "caller set this to default" is essential. The same
  resolved value must NOT trigger the same code path in both cases or
  legacy tests will fail. The `_resolve_channel -> (str, bool)`
  pattern made the distinction explicit and is reusable for any
  similar future extension.

- **Lesson 42** - `vi.mock` factories cannot reference top-level
  `const` declarations because the factory is hoisted above the
  declaration. Use `vi.hoisted()` to define fixture refs that the
  factory can read. Document this in any frontend test that mocks a
  module with non-trivial fixture data.

- **Lesson 43** - Reset-on-close beats reset-on-open for modals. The
  React 19 lint rule `react-hooks/set-state-in-effect` blocks the
  `useEffect(() => { setState(...) }, [open])` pattern. Reset state
  in the close handlers (cancel / submit / X / backdrop) instead -
  same effective behaviour, lint-clean, and easier to reason about.

- **Lesson 44** - Backend doc-comments referencing deleted frontend
  pages do not break anything but rot fast. The reference-purge
  re-grep gate in the prompt is frontend-only for a reason: backend
  comments are historical documentation and do not constitute "dead
  references". Update the user-facing strings (error messages, log
  lines that mention the page); leave docstrings alone.

- **Lesson 45** - When dropping a UI column during a redesign, audit
  every state the old column expressed. The v6.3.5 Team & Roles redesign
  dropped the Status column intending to lift "linked / consented" into
  the new WhatsApp pill, but the old "Active / Inactive" axis (driven
  by `User.is_active` / soft-delete state) had no replacement. Result:
  a regression where soft-deleted users stayed visible. Fix
  retrospectively was one filter line - but the lesson is preventive:
  before deleting a column, write down EVERY state value it could hold
  and confirm each has an explicit destination.

- **Lesson 46** - "All tests pass" + "lint clean" + "tsc clean" is the
  floor, not the ceiling. The three v6.3.5 bugs (consent handshake
  broken, duplicate-phone 500, soft-delete UI ghost) all shipped past
  537 backend tests + 24 frontend tests + tsc + lint without a single
  red. Each was caught only by running the actual workflow against a
  live DB in a real browser. Lesson 34 (live E2E) is non-negotiable
  before tag - and v6.3.5 pays its second dividend on that rule.
