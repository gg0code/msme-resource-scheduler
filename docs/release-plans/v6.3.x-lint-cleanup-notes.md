## Important meta-finding — ESLint react-hooks rules cascade-suppress

When one `react-hooks/*` rule fires on a callback or effect, ESLint stops reporting other rules in the same dependency chain. Fixing the surface-level error often reveals 1-2 previously-hidden errors in the same file. This means the "42 problems" baseline is a **lower bound** — the true count after a clean sweep will be higher.

Plan accordingly: budget extra effort per file vs. raw error count.

## File 5 — `src/components/onboarding/OnboardingContext.tsx`

### Deferred to v6.3.x

#### 1. `61:7 react-hooks/set-state-in-effect`

**Code:**
```tsx
useEffect(() => {
  if (user) {
    setSeenStops(loadSeenStops(user.id))   // <-- flagged
  } else {
    setSeenStops(new Set())
  }
}, [user?.id])
```

**Why deferred:** Real issue, not a false positive. Unlike AuthContext's flagged effect (which is async — setState happens after `await`), this one calls setState synchronously in the effect body, which is the exact "cascading render" anti-pattern the rule was written for. Each user-id change triggers: render → effect → setState → re-render. Two renders for what could be one.

**This is the textbook "you might not need an effect" case.** localStorage reads are synchronous; the seenStops set can be derived directly from `user?.id` in render via `useMemo`.

**Recommended fix when we come back:**
```tsx
// Replace useState + useEffect pair with useMemo derivation
const initialSeenStops = useMemo(
  () => (user ? loadSeenStops(user.id) : new Set<string>()),
  [user?.id]
)
const [seenStops, setSeenStops] = useState<Set<string>>(initialSeenStops)
// Then keep markSeen / resetTour mutating local state as today; the
// useMemo only seeds the *initial* state per user-id change.
```

Or simpler: a `useState` initialiser that captures the first-render value and a `useEffect` that calls `setSeenStops` only when `user?.id` changes from the previous render (not on initial mount). Tradeoff between readability and lint compliance.

**Behavior risk of refactor:** Tour-stop reload timing shifts from "after commit" to "during render" of the user-change render. localStorage.getItem is synchronous, so timing is fine — the only observable difference is that the *first* render with a new user already has the right stops, instead of needing one extra render to populate. Pure improvement.


**Why deferred:** Paired with #1. ESLint wants the full `user` listed (because the body references `user`, not just `user.id`). The useMemo refactor in #1 makes this go away.

**Standalone fix if not refactoring:** Change `[user?.id]` to `[user]` — but that re-runs the effect every time the user object identity changes, which happens on every silent-refresh response. Less efficient than `[user?.id]` but lint-clean.

#### 2. `161:5 react-hooks/set-state-in-effect` on `setDetailLoading(true)`

**Code:**
```tsx
useEffect(() => {
  if (!expanded || jobDetail) return
  setDetailLoading(true)         // <-- flagged: synchronous setState
  apiClient.get(JOBS.detail(job.id))
    .then(r => setJobDetail(r.data))
    .catch(() => {})
    .finally(() => setDetailLoading(false))
}, [expanded, job.id, jobDetail])
```

**Why deferred:** Real anti-pattern. `setDetailLoading(true)` runs synchronously in the effect body, triggering a cascading render before the fetch even starts.

**Recommended fix:** Restructure so loading is set in the click handler that triggers `setExpanded(true)`, not in the effect that reacts to `expanded`. Or: change to a pattern where the loading state is derived from a tanstack-query `isFetching`. Either way it's a behavior refactor, not cosmetic.

**Behavior risk:** Currently the loading spinner shows after one extra render. Refactor would make it appear on the same render as expansion. Pure UX improvement, but worth manual UI verification.
